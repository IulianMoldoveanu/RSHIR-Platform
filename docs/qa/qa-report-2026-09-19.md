## Report-only findings (prioritized)

### [P2] NEW migration name collision at `20260810_001`

**Where:** `supabase/migrations/`
**Symptom:** Two migration files share the same sequence prefix `20260810_001`:
```
20260810_001_dispatch_sweep_restore_guards_and_ready_clock.sql
20260810_001_see_the_order_no_courier_can_take.sql
```
On a fresh Supabase restore, the apply order between these two is non-deterministic (filesystem sort or Supabase lexicographic ordering). If one depends on the other's DDL, the restore can fail silently or with a schema mismatch.

**Suggested fix:** Rename `20260810_001_dispatch_sweep_restore_guards_and_ready_clock.sql` → `20260810_002_dispatch_sweep_restore_guards_and_ready_clock.sql` (or vice versa), verify the content doesn't have a cross-dependency requiring a specific order, then apply on all Supabase environments.
**Why not auto-fixed:** Migration renames require re-apply verification on all Supabase environments; human must do this.

> Note: the prior 19 duplicate prefix groups from `20260504`–`20260609` remain as carry-over from the 2026-05-30 report; this is a *new* `20260810_001` collision added since that report.

### [P2] `reconcileCardPayment` missing legacy column fallback

**Where:** `apps/restaurant-admin/src/app/dashboard/orders/actions.ts:397`
**Symptom:** The first payment reconciliation function (`markCodOrderPaid`, line 306) has a defensive try/catch that handles the case where `payment_method` or `payment_status` columns are missing (migration 20260504_001 not yet applied). The second function (`reconcileCardPayment`, line 397) uses the same `.select('id, payment_method, payment_status')` query but throws directly on `readErr` with `friendlyDbError`, with no column-missing detection path.

If the column migration hasn't applied on an environment where a CSR tries to manually reconcile a CARD payment, the action will throw a database error instead of gracefully falling back.

**Suggested fix:** Mirror the defensive pattern from `markCodOrderPaid` (lines 306–325): wrap the select in a try/catch, test `readErr.message` against `/payment_method|payment_status/i`, and return a user-friendly message rather than throwing.
**Why not auto-fixed:** This is in the payment reconciliation path — any edit to payment logic requires Iulian's explicit sign-off per the §5 guardrails.
