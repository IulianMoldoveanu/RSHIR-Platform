## [SECURITY] Report-only findings

### [P1] SECURITY: `settings` column anon grant leaks unsanitized tenant settings via direct table read

- **Where:** `supabase/migrations/20260725_001_v_tenants_storefront_invoker_flip.sql:59` (PR #952) · Codex comment `discussion_r3648336554`
- **Symptom:** The migration grants `SELECT (... settings)` at the table level to the `anon` role. While `v_tenants_storefront` correctly strips `cod_caen / cui / reg_com / legal_company / legal_address / legal_postal_code / email_notifications_enabled / onboarding / pause_reason` from the settings JSONB, a direct PostgREST call bypasses the view:
  ```
  /rest/v1/tenants?select=settings&status=eq.ACTIVE
  ```
  would return the **raw, unsanitized `settings`** JSONB for any ACTIVE tenant, exposing all of the above fiscal/legal fields to the public.
- **Status:** PR #952 notes this was already **APPLIED + VERIFIED LIVE** on prod (`qfmeojeipncuxeltnvab`) on 2026-07-24.
- **Suggested fix (requires human review):** Remove `settings` from the column-level GRANT on `public.tenants`, and instead expose sanitized settings only via `v_tenants_storefront`. The view already applies the sanitization; consumers should query the view rather than the base table. A follow-on migration would:
  1. `REVOKE SELECT (settings) ON public.tenants FROM anon;`
  2. Verify no storefront code queries `public.tenants.settings` directly (they all go through `v_tenants_storefront` already per the PR's own callsite audit).
- **Why not auto-fixed:** `supabase/migrations/**` is a protected path; migrations are never auto-written. This also requires a new migration, not a code change. Human decision: does the existing live prod state need an emergency patch migration?
